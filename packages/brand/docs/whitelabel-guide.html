Make this app yours

Clone the repo, type one command, answer five questions. You get a shippable app under your own name, icon and colour — bundle IDs, package names, deploy config and all. The renaming is done by a script, not by hand, so it is repeatable and you can undo it with one git checkout.

Before you start

Four things to have ready.

  • A name. Everything else defaults from it.
  • A bundle ID in reverse-DNS form, like com.acmerobotics.vision. This is effectively permanent once your app is in a store, so pick it deliberately.
  • A website, contact email, and your fork's repo URL.
  • A logo — a square PNG of at least 512px, or an SVG. Optional: if you have nothing, the tool draws a placeholder monogram so the app still builds, and reminds you to replace it.
Heads up

Two things in this repo are gitignored, so a fresh clone can't build until you create them. This is true before any rebranding — it isn't something the tool breaks.

apps/mobile/.env (copy from .env.example) and apps/mobile/android/key.properties. The Android one is needed even for a debug build. Both are listed in the checklist the tool generates for you.

1

Clone and install

Install first — the tool refuses to run otherwise.

terminal 
$ git clone https://github.com/fpv-labs/stera-app my-app
$ cd my-app
$ bun install

Then commit, so the rebrand lands on a clean tree. That is what makes it revertable in one move — and the tool will stop and ask you to do this if you skip it.

terminal 
$ git add -A && git commit -m "starting point"
2

Run /whitelabel

Open Claude Code in the repo and type it.

claude code 
> /whitelabel

It asks a short set of questions and writes your answers to packages/brand/brand.json. It doesn't rename anything itself — that's the script's job in step 4.

What's it called?

Name and company. The tagline too, if you want to change it.

Bundle ID?

It suggests one from your name and website. You can correct it.

Links?

Website, contact email, your fork's repo. Terms and privacy URLs derive from the website.

Accent colour?

One hex. The palette is near-monochrome by design, so this is the only colour decision.

Logo?

Point at a file, or have one drawn for you as a placeholder.

Existing users?

Only asked if relevant. Says whether to keep local data compatible. See below.

Before writing anything it shows you what it worked out from your answers, because several are awkward to change later:

3

Look at it

Nothing is written yet.

Before anything touches your tree, render the brand as a page:

terminal 
$ bun run brand:preview

That writes packages/brand/preview.html — open it directly, no server needed. It shows your launcher icon under the iOS and Android masks, your mark on light and dark plates, mock splash, sign-in, home and profile screens in both modes, every colour token with its WCAG grade, the type specimens, the radius scale, and a table of exactly what changes.

This is the loop. Edit brand.json, re-run the preview, look, repeat. It applies nothing, needs no artwork pipeline and works on a dirty tree, so it costs you seconds and commits you to nothing. Only once you like what you see is it worth printing the plan:

terminal 
$ bun run brand:check

That last line is the interesting one. On the first run only, the tool moves every hard-coded brand string out of the UI and into one generated file, then points the app at it:

Before 
Text("Stera", style: …)

BorderRadius.circular(12)

fontFamily: "EBGaramond"
After

fontFamily: BrandFonts.display

Which is why changing your mind later is cheap — it regenerates a handful of files instead of rewriting thirty. Every colour, every corner radius and every typeface in the app becomes reachable from brand.json.

4

Apply it

The only step that writes anything.

terminal 
$ bun run brand:apply

It renames directories, rewrites the tokens, generates every icon size for both platforms, updates the deploy config, and rebuilds the lockfiles. Then it stops.

Note

It never commits. Read git diff yourself and commit when you're happy. If you hate it, git checkout . puts everything back.

If a step fails, the error tells you whether it failed while planning (nothing was written — just fix and re-run) or while writing (the tree is half-done — fix and re-run, repeating a finished step is safe).

5

Verify

Fourteen checks, then a real build.

terminal 
$ bun run brand:verify --full
$ cd apps/mobile && flutter build apk --debug

Most of these catch things no compiler will. A background-upload task ID that stopped matching between Info.plist and the Swift that registers it compiles perfectly and simply never runs.

Bonus

The repo currently ships three different app IDs — one on Android, another on iOS, a third in the Play Store update link. The rebrand collapses all three onto your single bundle ID, and the check above keeps them that way.

6

Finish by hand

Everything needing an account only you can open.

The tool writes packages/brand/TODO.md with your names already filled in. The ones that block a first build:

  • □Android keystore → android/key.properties. Needed even for debug.
  • □Copy .env.example to .env in apps/mobile.
  • □Apple team ID if you're building for iOS. It is deliberately left blank rather than pointing at someone else's team.

And the ones that can wait until you're actually shipping: Apple App ID and Sign in with Apple, Google OAuth clients, R2 buckets, Postgres, DNS, and the store listings.

What's in brand.json

Five required fields. Everything else has a sensible default.

FieldWhat it does
brand.nameRequiredYour product name. Nearly everything else derives from it.
identifiers.bundleIdRequiredReverse-DNS app ID, used on both platforms.
urls.websiteRequiredTerms, privacy and API hostnames derive from this.
urls.contactEmailRequiredShown in the app.
urls.sourceRepoRequiredWhere the in-app “view source” link points.
brand.legalEntityCompany name. Defaults to the product name.
theme.brandAccentLightYour accent. Run bun run brand:accent <artwork> to read one straight off your logo; the dark variant is derived by lifting it.
theme.tint0–1, and the one that matters. How much of your accent bleeds into the greys. 0 keeps Stera's palette exactly; 0.6 makes the page background visibly yours. Semantic colours never take tint.
theme.shape.stylesharp, soft (as-is), rounded or pill. Changes the corner radii across the app.
fonts.displayThe headline face. The cheapest change that stops your fork looking like this one. Supply files under fonts.files for a family the app doesn't already bundle.
assets.iconSourceSquare PNG (512px+) or SVG. Every icon size is generated from it, and the in-app logo falls back to it, so one file is enough.
assets.logoDarkOnly needed if your mark disappears on a dark background. The preview shows you whether it does.
theme.overridesPin any individual colour token, if the accent and tint aren't enough.
urls.playStoreAppIdPlay Store listing id, once you have published. Must equal your bundleId — the updater looks the listing up by the id the running app was built with. Leave it out and Android update checks stay off.
urls.appStoreIdApp Store numeric id. Leave it out and iOS update checks stay off.
urls.updateFeedA Sparkle-style appcast XML feed, for shipping outside the stores. Wins over both store ids. With none of these three set — the default — the app never checks for updates and never prompts, which is what you want until you have somewhere to send people.
attribution.enabledWhether the small “Powered by Stera” credit shows in-app.

The file has a schema attached, so your editor will autocomplete the fields and show these descriptions inline.

—

Changing it later

Edit and re-run. It handles rename-to-rename.

Edit packages/brand/brand.json and run brand:apply again. It remembers what's currently applied, so a second run maps your old name to your new one rather than getting confused about the original. Re-running with nothing changed does nothing at all:

output 
Nothing to change - the tree already matches packages/brand/brand.json.
If you have users

Three renames affect data already on people's phones: the local database filename, the recording format's schema names, and saved iOS folder bookmarks.

For a brand new fork this doesn't matter. If you're pushing an update to an existing install base, say so during the interview and those are left alone. Old recordings stay readable by default either way.

—

What it won't do

On purpose.

It won'tBecause
Touch your signing keysThe Apple team ID is blanked, not inherited. A build signed against someone else's team is worse than one that won't sign.
Write real secretsOnly .env.example files are touched. You fill in the real ones.
Remove the licenceRetaining the copyright notice is a condition of the licence, not a courtesy.
Run on uncommitted workSo a single git checkout . always undoes it.
Edit lockfiles as textbun.lock contains the word sisteransi. Find-and-replace would quietly corrupt it, so they're rebuilt instead.
CommitReviewing the diff is your call.

You can turn off the in-app credit with attribution.enabled: false. That hides the line in the profile screen and nothing else — the licence and copyright notice still have to stay.

—

If something goes wrong

The four you're most likely to hit.

You seeDo this
dependencies are not installed Run bun install. Without it, the image library resolves to a build that crashes partway through generating icons.
the working tree has N uncommitted change(s) Commit or stash. This is the guard that keeps the rebrand undoable.
null cannot be cast to non-null type kotlin.String Create apps/mobile/android/key.properties. Unrelated to the rebrand — a fresh clone does this too.
these generated files have been edited by hand Move your change into brand.json, or pass --force to discard it. Files marked do not edit are checksummed.

Start over entirely with git checkout . and rm packages/brand/.applied.json.
